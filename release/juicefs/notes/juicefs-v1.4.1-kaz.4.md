# juicefs-v1.4.1-kaz.4

v1.4.1-kaz.3 に、キャッシュが空のときの読み込み（VM の cold boot など）で、object storage からのダウンロードの無駄と、止まった応答の待ちを減らす改修を加えた版です。kaz.3 までの改修は、すべてそのまま含みます（[v1.4.1-kaz.3](https://github.com/tongsama/juicefs_inspection/releases/tag/v1.4.1-kaz.3) のリリースノートを参照）。この版から、タグの名前は製品ごとの形（`juicefs-v…`）です。

## 追加したオプション（どちらも既定では無効）

- `--kaz-finish-canceled-get`（既定 `false`）
  - 先読みが不要になって取り消されたブロックのダウンロードを、途中で捨てずに最後まで取り、ディスクキャッシュに入れます。取り消された read はすぐに戻ります。
  - ダウンロードの枠を待っている間に取り消されたものは、取りに行きません。最後まで取り続けるダウンロードは、`--max-downloads` の半分までです。それを超えた分は、従来どおり取り消します。
  - 同じブロックを待っていた別の read に、先に出た read の取り消しが伝わって失敗する問題も、このオプションで直ります。
  - ディスクキャッシュが必要です。metrics: `juicefs_kaz_canceled_get_finished`、`juicefs_kaz_canceled_get_dropped`。
- `--kaz-get-header-timeout=<時間>`（既定 `0` = 無効、例 `10s`）
  - ブロックのダウンロードで、応答ヘッダが返るまでの待ちだけを制限します。時間を過ぎたら、その要求をやめて、通常の再試行で取り直します。
  - **`--get-timeout` との違い:** `--get-timeout`（既定 60s）は、ダウンロード全体（応答を待つ時間と本体を受け取る時間の合計）の上限です。`--kaz-get-header-timeout` は、データが流れ始めるまでの待ちだけの上限です。遅くても流れている本体の受け取りは切りません。
  - 全体共通の HTTP client の応答ヘッダの待ち（30s 固定）は、PUT・DELETE・LIST と全部の object storage に効くので、変えていません。
  - 正常なダウンロードの時間より十分長く設定してください。metrics: `juicefs_kaz_get_header_timeouts`。

VM イメージの用途では、`--kaz-finish-canceled-get --kaz-get-header-timeout=10s` の組み合わせを想定しています。

## 既定で変わる動作

- ブロックのダウンロードのエラーを包むときに、元のエラーの種類を保つようにしました（`%w`）。ログの文言は変わりません。

## 計測結果（キャッシュが空の状態からの VM の起動、qcow2、virtio）

rclone serve s3 → Google Drive の構成です。各条件の計測はそれぞれ 1 回だけで、Drive の応答の速さは時間帯で大きく変わります。数字は目安です。

| | `--kaz-get-header-timeout=10s` のみ | 2つとも有効 |
|---|---:|---:|
| 起動時間 | 約 20 分 | 約 10 分 |
| Drive へのダウンロード | 2,221 | 1,426 |
| そのうち途中で捨てたもの | 760 | 0 |
| QEMU の遅い read の待ちの合計 | 9,894s | 4,469s |

- 2つとも有効にした回は、Drive の応答も速い時間帯でした（ダウンロードの中央値 1.70s → 1.33s）。そのため、起動時間の差がすべてオプションの効果ではありません。ダウンロードの減少は、オプションの効果です。
- Drive の応答が止まりやすい時間帯の参考の計測では、10s で切った 35 件のうち 21 件が 0.7〜2.2s で取り直せました。同じ object への要求が約 30s まとめて止まる場合は、取り直しても同じように止まります。

## 注意

- `--kaz-finish-canceled-get` は、取り消された分もキャッシュに入れるので、キャッシュの使用量が増えます。キャッシュが小さいと、ほかのブロックの追い出しが増えることがあります。
- `--kaz-get-header-timeout` で切った要求は、rclone serve s3 の中では Drive からのダウンロードが続きます（rclone 側で止める改修は、別に検討中です）。
- このほかの注意（Windows 版の mount は未検証、armv7・macOS 向けはなし、稼働中の mount の置き換えなど）は kaz.1 と同じです。
