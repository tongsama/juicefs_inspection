# キャッシュ cold の VM 起動の解析（2026-10-08）

対象: VM `ubuntu26-test`（qcow2、JuiceFS の inode 614590、disk は `bus='sata'`・`cache='unsafe'`）。ユーザーがキャッシュがほぼ空の状態で起動した。JuiceFS の `.accesslog` と DEBUG ログ（21:21:08〜21:48:13）を解析した。証跡は [manifest](manifest.json)。

## 観測事実

### 読み込みの遅さ

- 起動にほぼ 26 分。QEMU の read 22,047 回（約 1.6GiB）、そのうち 50ms を超えたのは 3,203 回。遅い read が処理中の時間は合計 1,576 秒で、ほぼ全期間にわたる。
- 遅い read の同時数は、時間の 43% が 1 本、59% が 2 本以下。
- object の GET は 1,351 回（うち 4MiB の block が 1,294 回、約 5.3GiB）。QEMU が読んだ量の約 3.5 倍。zstd 圧縮のため、小さい read でも block 全体を取る。
- GET 1 回の時間は中央値 1.9s、p90 3.4s、最大 30.0s。GET の同時数は 1〜2 本が時間の 72%（上限 `--max-downloads 60` には遠い）。
- 同時数が 1 本でも 8 本でも、GET 1 回の中央値は 1.9〜2.3s でほぼ変わらない。合計の速度は最大 23.8MiB/s。帯域ではなく、往復の遅延が律速している。
- すべての GET が、QEMU の遅い read と時間が重なっている。compaction だけが原因の GET は、この区間では見えない。
- Read 前の flush 待ちのうち 50ms を超えたものは 222 回、合計 21s、最大 0.2s。今回の遅さの主因ではない。
- キャッシュの上限に達し、1,791 block が追い出された（年齢の中央値 13,651s。600s 未満のものは無い）。今回取った block が追い出されて取り直しになった例は無い。
- GET の失敗は 8 回。いずれも `exceeded maximum number of attempts, 1`（StatusCode 0 または 500）で、うち 30.0s ちょうどで切れたものがある。

### ゲストの I/O エラーとの対応

ゲストの dmesg（[抜粋](guest-dmesg-excerpt.txt)）の SATA コマンドのタイムアウト（`cmd_age=30〜33s`）は、ゲストの起動時刻を 21:22:56 頃と置くと、ホストで約 30 秒かかった操作と 3 回とも一致する。

| ゲスト（秒） | ホスト | ホストの `.accesslog`（すべて OK） |
|---|---|---|
| 1011.58 | 21:39:48.1 | read 32.0s、write 31.8s |
| 1186.26 | 21:42:40〜41 | read 約 27.5s が 7 件、write 27.7s |
| 1230.92 | 21:43:27.4 | read 31.4s |

ホスト側の JuiceFS は、どの操作でもエラーを返していない。遅れて OK を返している。ゲストは SATA のコマンドタイムアウト（Linux の既定は 30 秒）で、リンクをリセットして I/O エラーとして扱った。その結果、ext4 で journal abort が起き、read-only になった。

## ソース上の条件

- `--prefetch` が働くのは、Range GET（`loadRange`）が成功したときだけ（`pkg/chunk/cached_store.go:768`）。Range GET は圧縮なしのときだけ使う（`seekable`、`cached_store.go:867`、`:155`）。そのため zstd の volume では `--prefetch` は効かない。
- ファイルの readahead は、順番に読んでいると判定されたときだけ大きくなる（`pkg/vfs/reader.go:419-435`）。
- ディスクキャッシュの LRU の時刻は、稼働中はメモリ上にある。再起動したときは、block ファイルの atime を初期値にする（`pkg/chunk/disk_cache.go:1060`）。JuiceFS は atime を書き戻さない。キャッシュディレクトリは ext4 の relatime なので、ディスク上の atime は粗い。

## 推測（未確認）

- read の後ろで write も約 30s 待っている。これは QEMU の qcow2 がメタデータの読み込みを待った巻き添えだと推測する。
- ゲストは「失敗した」と判断したが、ホストでは遅れて成功した書き込みがある。そのため、ゲストの ext4 に不整合が残る可能性がある。fsck が必要。

## 改善の候補

- 再発防止: ゲストの disk を virtio にする（ユーザーは virtio のつもりで作っていたが、実際は sata だった）。または、ゲストの `/sys/block/sdX/device/timeout` を延ばす。
- 隣の block の先読み: GET のうち 692 回（51%）は、同じ slice の 1 つ前の block がすでに取得済みだった。そのうち 434 回は、前の block を取り始めてから 2s 以上後に要求されていた。粗い見積もりで、GET の待ちが 3〜4 割減る。ただし外れのダウンロードが最大で約 650 回増える。ユーザーはこちらを試す方針（起動で読む範囲の記録と再生は、汎用の仕組みにしにくいとの判断）。

## 追記: GET が 25〜30s かかる原因（rclone ログ、2026-10-08 調査）

rclone のログ（`/home/kwatanabe/.rclone_serve_s3.log`）を読み取りだけで解析した。対象は行 272337〜357626（21:21:33〜21:56:57）で、切り出した範囲の sha256 は `fc08282a12aab6ec016cdbebc891579fae7be2805e4711d888fb61b28985952a`。リポジトリには集計とスクリプトだけを置き、ログ本体は置いていない（[rclone_get/](rclone_get/)）。rclone のログは秒精度なので、時間には ±1s の誤差がある。

### 観測事実

- 4MiB の GET 1 回で、Drive への呼び出しは直列に 2 回。lookup（files.list、平均 0.5s）と、ダウンロード要求を出してから最初のデータが返るまでの待ち（平均 1.9s、p50 1s）。本体の転送は 1s 未満。
- JuiceFS で 15s を超えた GET は 35 件。35 件とも、ダウンロードの応答待ちが 15〜30s だった（lookup は 0〜3s）。
- 長い応答待ちの最中でも、後から始まった他の GET は約 1s で終わっている。tpslimit も pacer も到着順に枠を割り当てる仕組みなので、1 本だけが取り残されるとは考えにくい。そのため、Drive 側が個々の要求に遅く応答したものと推測する。
- 保持されているログ全体（約 1.8 万件）で、応答待ちの最大は 32s だった。10/07 のログには 5s 以上の待ちが無く、発生の多さは時期によって違う。
- pacer、rate limit、403 の兆候は 0 件。ただし、tpslimit と pacer の待ちはもともとログに出ない。
- Drive API の呼び出しは約 15,450 回（平均 7.3/s）。内訳は PUT 系 50%、DELETE 系 26%、GET 系 25%。21:33〜21:40 は分平均 16〜20/s で、上限の 20/s に張り付いていた。この間は GET 1 回あたり約 1s 遅くなったが、25〜30s の遅れの原因ではない。20/s の上限は `--tpslimit 20` と、rclone.conf の `pacer_min_sleep = 50ms` の 2 か所でかかっている。
- StatusCode 500 の 2 件（compaction の読み出し）は、lookup では見つかったファイル ID が、ダウンロードで Drive の 404 になったもの。この slice の upload の経路は不明。
- JuiceFS は GET 774 件をキャンセルしたが、ログには残していない（`cached_store.go:818-820` が `logRequest` より前で return する）。rclone 側には、これに対応する `broken pipe` がある。

### ソース上の根拠

- 30s で切れているのは JuiceFS の HTTP client の `ResponseHeaderTimeout: 30s`（`pkg/object/restful.go:157`）。`--get-timeout 60` より先に切れる。S3 SDK の再試行は 1 回（`s3.go:587`）。
- rclone の serve s3 は、データを書き始めるまでレスポンスのヘッダを送らない。そのため Drive の応答待ちが、そのまま JuiceFS の 30s に数えられる。

### 改善の候補（未実施）

1. JuiceFS のヘッダ待ちの 30s を短くして再試行する。または、数秒後に同じ GET をもう 1 本出す（hedge）。失敗した 4 件の再試行は、1.2〜8.7s で成功していた。代償として API の呼び出しが増える。打ち切った側の Drive のダウンロードは、rclone の中で続く。
2. tpslimit と pacer_min_sleep を上げる。上限に張り付いたときの約 1s は減るが、25〜30s の遅れには効かない。403 のリスクがある。
3. API の呼び出しを減らす（PUT の前の lookup 3,514 件、キャンセルされた GET）。
4. rclone のログをマイクロ秒単位にして、待ちの内訳を測れるようにする。
