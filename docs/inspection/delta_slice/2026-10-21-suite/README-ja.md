# delta の設定の比較（流し直しの試験、2026-10-21）

本番の書き込みを記録して、試験の volume に設定を変えながら流し直した。道具は `tests/juicefs/`（`jfsmeasure`、`jfsreplay`）。

## 条件 [観測]

- 記録: 本番の VM の起動からアプリが使えるまでと、その後の利用（12:56〜13:14、約 18 分）。
  - `trace.tsv` は 168,259 操作で、write 72,412（5.2 GB）、read 95,134。SHA-256 の先頭は `0301656afd02c6fd`（本体は `tests/juicefs/results/20261021-trace1/`、git には入れない）。
  - 操作の時刻は `trace.tsv.marks.tsv` にある。起動 12:58:00、ログイン画面 12:58:56、ログイン完了 12:59:25、アプリ 13:02:02、apt upgrade 13:03:39〜13:08:13（765 MB の取得）、chrome のブラウジングと再起動 13:08:30〜13:13:30。
  - 取りこぼし: 全 inode の write が、記録 72,412 回に対して metrics 72,414 回（差 0.00%）。解析できなかった行は 0（`trace.tsv.meta.json`）。
- 種: write が触れた 316 chunk（19.75 GiB、`--written-only`）。Drive 側の占有は約 25 MB（圧縮後、ユーザーの確認）。
- 試験の volume:
  - メタデータは一時 Redis（docker compose、`redis:8.0.5`）で、RTT 10 ms の中継を通す。データは本物の Drive（rclone serve s3 のバケット `juicefs-kaz-test`）。
  - mount の実効設定（`.config`）は、試験用の path、port、compaction の値を除いて本番と同じ。
- 流し直しの忠実さ（記録の全体で、本番の記録との比較）:
  - write の中央値は 0.15〜0.21 ms（本番 0.035 ms）、99% は 36〜52 ms（本番 57 ms）。
  - read の中央値は 0.21〜0.31 ms（本番 0.14 ms）。
- 各回の前に、温めたキャッシュの写し（12.4 GB）を戻した。
- 本番の VM は止めた状態で流した。

## 読み取れること [推論、1 回ずつの結果]

- **trigger を下げるほど PUT の回数が減る。** trigger 30 は 99 より約 16% 少ない（7,493 → 6,305）。アップロード前に片付けた slice が増えた（13,151 → 14,161）。compaction を早めるとアップロード前の片付けが増える、というユーザーの見立てと合う。代わりに DELETE の回数が少し増える。
- **trigger 200 は PUT の回数が一番多い**（7,960）。片付けも一番少ない（11,857）。
- **block-ratio 0.75 は、書き直すブロックを約半分に減らした**（80 → 43）。代わりに段のバイトが倍近くに増え（125 → 238 MiB）、compaction の出力の合計はほとんど変わらない（0.46 → 0.42 GiB）。PUT の回数も変わらない。
- **block モードは、compaction の出力が delta の約 4.5 倍**（2.06 GiB と 0.41〜0.48 GiB）。一晩の本番の比較（6.53 → 0.56）と同じ向き。PUT の回数は、この試験の中ではほぼ同じ（7,316）。
- メタデータの操作の数と、流し直しの待ち時間には、はっきりした差が見えない。

## 限界 [未検証]

- 各設定 1 回だけで、ばらつきは分からない。同じ設定を 2 回流して（`--repeat 2`）幅を確かめる必要がある。
- 「未収束」の回は、落ち着くまでの待ちの上限（10 分）を過ぎても compaction の開始が止まらなかった（staging と uploading は 0）。その回の数は、まだ増える途中で区切られている。
- 種と書き込みの中身が作り物なので、PUT のバイト（圧縮後）は比べられない。回数で比べる。
- 記録は、1 回の起動と apt upgrade を含む 18 分だけ。ゲストの書き込みの形は日によって違う。
- 試験の間、本番と同じ rclone と Drive を使った。Drive の応答の時間切れ（PUT の 1 回ごとの失敗）は、どの回にも数件〜数十件あった（警告として記録した）。

## 実行中に直した道具の問題（`tests/juicefs`、commit 7b78eb9〜38f318f）

- 見張りが、compaction の片付けで打ち切られた PUT（`is not needed, abandoned`）をエラーとして数えていた → 除外した。
- 流し直しが本番より桁違いに遅かった（write の中央値 834 ms）→ 回し待ちをやめた。そのうえで 64 の worker process に分け、GIL の取り合いをなくした（0.17 ms）。
- 毎回 Drive からキャッシュを温めていた（13〜17 分）→ 写しを戻す方式にした（約 40 秒）。
- Drive の応答の時間切れや DELETE の 500 で止まっていた → 1 回ごとの失敗は警告にした（rate limit などでは止める）。
- umount の後に試験の mount の process が残り、次の mount の metrics の port が使えなかった → 試験の mount の `.config` の Pid／PPid で探して止めるようにした。juicefs の process の cmdline は 1 つの文字列に書き換えられ、255 文字で切れるので、cmdline からは探せない。本番の mount の Pid／PPid には決して signal を送らない。
