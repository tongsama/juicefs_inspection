# compaction の policy の実機計測と cooldown の削除（2026-10-14）

[2026-10-13 の調査](../2026-10-13/report-ja.md)の続き。kaz compaction policy（本体 `feat/kaz-compaction-policy`）を本番の VM で計測し、PUT の総数で比べた。[事実] は観測またはソースで確認したこと、[推論] は推定、[未確認] は確かめていないこと。

## 0. 結論

- **Read からの compaction の下限（`--kaz-compaction-read-min 100`）だけで、PUT の総数（ゲストの書き込み 1 MiB あたり）は 36.5 → 17.6（約 −52%）** [事実：各 1 回の計測]。
- **cooldown（書き込みの続く chunk の compaction を保留する）は逆効果**で、36.5 → 39.9 に増えた。compaction は、writeback の staging にあるアップロード待ちの小さな slice をまとめて片付けて（retire）、その PUT を省いている。保留するとその前にアップロードされてしまう。ユーザーの判断で cooldown をコードから削除した（本体 49908265）。
- `--upload-delay 60s` はアップロードされる割合を 29% → 18% に下げたが、反映の遅れが大きいので本番には入れない（ユーザー判断）。30s は誤差の範囲。
- 2026-10-13 の記録と TODO の「PUT 約 −88%」は compaction の PUT だけの値で、PUT の総数ではなかった（訂正）。

## `--kaz-compaction-read-min` の意味

Read で chunk の slice の一覧をメタデータから読み直したとき（open-file の chunk キャッシュのミス）、その chunk（64 MiB）に記録されている slice が指定値**以上**なら、バックグラウンドの compaction を要求する（scheduler の列に入れるだけで、inode ごとに 1 本ずつ順に実行される）。upstream の値は 5。数えるのは記録された slice の件数で、重なりを整理した後の断片の数ではない。キャッシュが効いている Read では何もしない。commit の側の compaction（99、199、… 個目、または 350 個超）はこのオプションと関係なく upstream のまま動く。

## 3. 仕組み

- [事実：ソース] writeback では、確定した slice はまず staging に置かれ、アップロードは並列 18 本（`--max-uploads 18`）で順に行われる。実測では 1 件 約 3.8 秒で、1 分あたり約 290 件で頭打ちになる（A の PUT は 1 分あたり 250〜370 件）。
- [事実：ソース] compaction が chunk をまとめると、まとめられた slice は `Retire`（2026-10-02 の改修）でローカルの staging から消され、アップロードされない。
- [推論] A では compaction が頻繁に動き、アップロード待ちの slice を半分以上片付けていた。cooldown（B）は、書き込みの続く chunk（journald）を force（700 個）まで保留するので、その間に slice がアップロードされ、片付けられる割合が下がった。
- [推論] read の下限（C）は、slice の少ない chunk を 64 MiB 書き直す無駄な compaction を減らす。inode ごとに 1 本しかない compaction の枠が、アップロード待ちの多い chunk に早く回るので、片付けられる割合が 52% → 71% に上がった。
- [事実：ソース] `--upload-delay` は、staging のブロックを指定時間がたってからアップロードする（見回りは指定値か 1 分の短いほうごと。実際の遅れは 30s 指定で 30〜60 秒、60s 指定で 60〜120 秒）。待つ間に compaction が来れば片付けられる。

## 4. 机上のモデル（`staged_sim.py`）

アップロードの待ち行列（並列 18、1 件 3.77 秒）と compaction による片付けを入れた。A の片付けの割合（52%）と書き込みの slice の PUT（3,624 に対して 3,593）を再現した。B の片付け（実測 34%、モデル 44%）と C（実測 71%、モデル 63%）は外れ、方式の差を小さめに見積もる（`staged_sim.out`）。

- cooldown の値（`cooldown_short.out`）: 2〜10 秒は read の下限だけとの差が ±5% で誤差の範囲、30 秒を超えると PUT が増える。
- upload-delay（`upload_delay.out`）: read の下限に足すと 30s で −6〜9%、60s で −11〜23%、120s で −18〜33%。
- staging の待ちで compaction を起動する案（アップロード待ちが 50 ブロック以上の chunk はすぐ compaction）は、モデルで −23〜26%。upload-delay と効き方が重なる。

## 5. 決定と残り

- ユーザー決定: cooldown は入れない（本体 49908265 でオプション、保留、見回り、`afterWrite` の hook を削除。commit の経路は upstream のままに戻した）。本番の設定は `--kaz-compaction-read-min 100` だけ。`--upload-delay` は本番に入れない。FUSE `writeback_cache` は使わない（以前遅くなった、動作が不明瞭）。
- 本体に残る差分（upstream 由来のファイル）: base.go +5/−1（struct 2 項目、metrics 2 行、Read の呼び出し名）、config.go +7、flags.go +5、mount.go +1。ビルド `1.4.1+2026-10-14.49908265`（sha256 `a74868b7…`）。
- 残りの候補: ブロック単位の compaction（変化した 4 MiB だけを書く。E では PUT の約 4 割が compaction の出力）、staging の待ちで起動する compaction。
- [未確認] 各 1 回の計測で、使い方（書き込みの量と密度、時間）がそろっていない。差の大きい結論（read の下限で −52%、cooldown で増加）は方向が確かと見るが、数 % の差は区別できない。
