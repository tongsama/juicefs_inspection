## 解釈

- [事実] raw では fallocate が 2 回とも 0 回。qcow2 の cluster 割り当てに伴う ZERO_RANGE（J・G で 37〜52 回、合計 6〜8 秒、freeze の約 1%）が無くなった。
- [推論] PUT の合計は 1 MiB あたり 16.8〜17.6 で、J・G（19.0〜21.1）より約 1〜2 割少ない。2 回とも J・G を下回ったが、同じ設定でも 10〜15% ばらつくので、効果は小さめに見ておく。
- [事実] R2 の区間は 2 分 53 秒で、J（約 3 分、分単位の記録）とほぼ同じ。この起動とアプリの起動では、所要時間の大きな差は見えない。upstream の K（9.4 分）からの改善は、主に block compaction による（10-14 の結論）。
- [事実] read は R2 で平均 15.4 ms／p99 108 ms と R より改善したが、J（10.1／106 ms）より平均は大きく、1 秒を超える read も多い（136 対 28）。GET は 42 回（J は 19 回）で、キャッシュのミスがまだ多い。[未確認] 2 回目でもミスが残る理由（compaction で作り直したブロックがキャッシュに入らない、など）は見ていない。
- [推論] 書き込みの遅延は R2 で平均 8.0 ms／p99 54 ms と J（4.3／53 ms）に近い。
- [事実：2026-10-07] Ubuntu のインストールのように cluster の割り当てが多い負荷では、raw の効果は大きかった（qcow2 84 分 → raw 36 分、fallocate 15,343 回 → 0 回）。体感の改善は、こうした書き込みの多い場面か、ゲストの中の操作で出ている可能性がある [推論、未確認]。

## 残り

- 2 回目でも GET（キャッシュのミス）が J の約 2 倍残る理由を確かめる。
- 体感で速くなった場面（どの操作か）を特定し、その操作を区間にして測る。
