# 計測の suite と、書き込みを流し直す試験の suite（設計）

日付: 2026-10-21。状態: 実装済み（2026-10-21 ユーザー承認の設計、このリポジトリの main に tests/juicefs/ として 18 commit、dfcfabf..561c90c。116 件の試験が通過。本物の Drive での試験はまだ）。実装で変えたこと（SDD の台帳の Ruling）: 取りこぼしの確かめは `fuse_written_size_bytes` と全 inode の write で行う（§5.1 の staging との比較から変更）、試験の volume の最初の format は `--create-bucket` を付けたときだけ、種のブロックの形は 4 MiB ごとの fsync で作る（block の compact は 64 MiB の record を分けないため）、種の後は upload が終わるまで待つ、run の見張りは本番の `object_request_errors` も読む、試験の volume は暗号化なし（本番は aes256gcm-rsa）。2026-10-21 ユーザーの依頼で、試験の Redis は docker compose（`tests/juicefs/replay/docker-compose.yml`、`redis:8.0.5`、127.0.0.1 だけに公開、project 名 jfs-kaz-test）で上げる形に変えた（§5.2 の「scratch の redis-server」を置き換え）。置き場所: このリポジトリの `tests/juicefs/`（ユーザー指定）。

[判断] は、この会話で agent が決めたこと。ユーザーが読んで直せるように印を付ける。

## 1. 目的

差分方式の compaction（`--kaz-compaction-mode delta`）のノブ（trigger、block-ratio など）を、**10〜15 分の試験で、同じ条件で比べられる** ようにする。一晩の本番の計測は長すぎて回せない（ユーザー）。本番の 10〜15 分では、ゲストの書き込みの違いの方がノブの違いより大きく出る。

あわせて、本番と試験のどちらにも使える **計測の suite** を作る。今はばらばらの道具を、1 つにまとめる。ばらばらの道具とは、metrics の記録、record の数、キャッシュの出入り、再起動の直前の内訳、`progress_kaz.sh`、比較、起動の解析のこと。2026-10-21 には、前回の比較の材料をそろえず、ユーザーが比べられなかった。そうならないように、材料がそろっているかを道具が確かめる。

## 2. 成功の基準

- 1 つのコマンドで、設定の組（既定は §5.5 の 6 つ）を順に流し、設定ごとの数字を 1 枚の表で比べられる。1 つの設定は 10〜15 分。
- 本番の計測は、開始・状態の確認・経過の表示・再起動の直前の記録・区間の比較が、それぞれ 1 つのコマンドでできる。開始の時点で、前回と同じ材料がそろっていることを道具が確かめる。
- 本番の metadata、object storage、キャッシュ、staging、元のログを変えない。本番の mount には読み取りだけで触れる。

失敗とみなすこと:

- 本番の Redis や本番のバケットに書き込むこと。
- 試験で Drive の API の回数制限に当たり、本番の I/O を目に見えて遅くすること。§6 で、並列の数を本番以下に抑える。
- 数字の出どころ（どの区間、どの系列）が表から分からないこと。

## 4. 計測の suite（`tests/juicefs/measure/`）

1 つの CLI `jfsmeasure` にまとめる（sub-command 形式）。対象の mount は、プロファイルで指定する。[判断]

- `prod`: 本番。metrics は 127.0.0.1:9567、VM のディスクは inode 634040、キャッシュは `~/.juicefs/cache/<UUID>`、メタデータの接続は `~/utilities/cloudfs/juicefs_mount.sh` の `MOUNT_FROM` から読む。
- `test`: 試験の mount（§5）。

| sub-command | すること |
|---|---|
| `start <profile> <出力ディレクトリ>` | 常駐を起動する: metrics（60 秒ごと）、LLEN の分布（10 分ごと）、キャッシュの出入り（5 分ごと）。開始の時点の `/metrics` の全体と、キャッシュの内訳も取る。mount の設定は `<mountpoint>/.config`（動いている mount の設定の JSON。ユーザーの指摘、2026-10-21）を写して `config.json` に残す（接続先や鍵らしい項目は伏せる）。PID と開始の条件（バイナリの version と sha256、起動時のログの kaz の行、出力の場所）を `run.json` に書く。`compare` は、2 つの区間の `config.json` の違いも表に出す |
| `check <出力ディレクトリ>` | 常駐が全部生きているか、各記録が最後に更新された時刻、足りない材料を出す。足りなければ 0 以外で終わる |
| `stop <出力ディレクトリ>` | 常駐を止める |
| `capture <出力ディレクトリ> <ラベル>` | 再起動の直前の記録: `/metrics` の全体、キャッシュの内訳とファイルの一覧、kaz-2q の管理ファイルの写し |
| `progress <出力ディレクトリ> [開始] [終了]` | `progress_kaz.sh` と同じ項目に、compaction の項目を足して表示する。足すのは、delta と block の結果、書き直しの理由、段のバイト、まとめ直し、片付けた slice の数、staging 1 GiB あたりの量、PUT・GET・DELETE、メタデータの操作の数と所要時間、record の数の分布。既定の区間は「開始から今まで」と「直近 1 時間」 |
| `boot <出力ディレクトリ> <開始> <終了> [ラベル]` | 起動の区間の解析: GET、ミス、ヒット率、ghost_hit の内訳、GET で補充した量。補充した量は、キャッシュの出入りの記録から、以前キャッシュにあって消えたものとそれ以外に分ける（今の `boot_analysis.py`）。ユーザーが言う 4 つの時刻を引数で受け、表に入れる |

## 5. 流し直しの試験の suite（`tests/juicefs/replay/`）

### 5.1 書き込みの記録（`record`）

- 本番の mount の `.accesslog` を読み、VM のディスクの inode の操作を `trace.tsv` に書く。ほかの行は捨てる。読み取りのみ。
  - 対象は `write`、`read`、`fsync`、`flush`、`fallocate`、大きさを変える `setattr`（truncate）。
  - 各行の時刻・位置・長さ・所要時間を書く。
- [source、builder check で確認] `.accesslog` の形式:
  - write／read は `(ino,size,off,fh)` で、大きさが位置より前。fallocate は `(ino,mode,off,size)`。
  - truncate は `truncate` では出ず、`setattr (ino[fh],0xMASK,[size=N,...])` として出る。
  - read の末尾には `: n` と `: (n)` の 2 つの形がある。
  - 行の時刻は操作が終わった時刻。開始の時刻は「終わった時刻 − 所要時間（`<秒>`）」で戻す。流し直しは開始の時刻で並べる。
  - 読む側の buffer は 10,240 行で、あふれた行は黙って捨てられる。
- 取りこぼしへの備え [判断]:
  - 記録は、読んだ行をすぐ絞り込んで書く常駐にして、遅れを作らない。
  - 記録の後に、取りこぼしを確かめる。記録の中の write の回数とバイトを、同じ区間の本番の metrics（staging への書き込みの量、FUSE の操作の数）と突き合わせ、差を報告に出す。差が 1% を超えたら、その記録は使わずに取り直す。
- 開始と停止は手で行う。ユーザーの合図で始め、VM を再起動して、アプリが使えるまで使い、10〜15 分で止める。
- 記録には、ユーザーが言う 4 つの時刻（起動の開始、ログイン画面、ログイン完了、アプリが使える）も入れられるようにする。
- 同時に計測の suite（`prod`）も動かす。本番の側の数字（PUT の回数など）を、試験の数字と突き合わせられるようにするため。

### 5.2 試験の volume（`testvol`）

- **Redis:** 一時的な Redis を、scratch の場所に置いた redis-server で起動する（今回と同じ 8.0.5 の展開物）。手前に RTT を足す中継（`rtt_proxy.py`）を置く。
  - 中継は、往路・復路それぞれで、受け取った塊を指定の時間（既定 5 ms ずつ、往復 10 ms）だけ遅らせて送る。順序は保つ。pipeline の塊はまとめて遅らせるので、本番と同じく pipeline の効果が残る。
  - ポートは本番と重ならない値にする（例: Redis 16379、中継 16380）。
- **object storage:** `rclone serve s3`（本番と同じ endpoint）に、試験専用のバケット（既定 `juicefs-kaz-test`）を作る。鍵は rclone の起動スクリプトから読み、表示しない。
- **volume:** `juicefs format` で、上の Redis（中継の port）と試験用のバケットに作る。block size、圧縮、trash-days は本番と同じにする（本番の format の値を `juicefs status` で、読み取りのみで確かめる）。本番の format は trash-days 0 の記録がある（mount のスクリプトの注釈）。trash-days 0 なら、clone を消したときの後始末は trash を経ない。本番が 0 でなかった場合も、試験の volume は 0 にする。[判断]
- **mount:** 本番の mount のスクリプトのオプションの一覧を、試験用の設定ファイル（`mount_flags.txt`）に写して使う。compaction の設定だけを差し替える。
  - キャッシュのディレクトリと mountpoint は、本番とは別にする。metrics の port も別にする（例: 9568）。
  - 本番のスクリプトから写す手順（差分を目で確かめる）は README に書く。[判断]

### 5.3 種のファイル（`seed`）

- 記録が触れた chunk（64 MiB 単位）だけに、元のデータを書いた種のファイルを、最初に 1 回だけ作る。長さは VM のディスクと同じにして、触れない範囲は穴のままにする。
- 中身は、圧縮のよく効く決まったバイト列にする（ユーザーの決定）。
- 書いた後に、`--kaz-compaction-mode block` で mount した状態で `juicefs compact` をかけ、chunk を 4 MiB のブロックごとの record（本番の今の基本の形）にする。§5.4 で clone の元にするため、その後は書き換えない。[判断。builder check の指摘: upstream mode の compact は chunk 全体を 1 つの slice にするため、block mode で行う]
- 対象の chunk は、記録の write と read が触れた chunk の全部。読むだけの chunk も含める。キャッシュを温めるときと、流し直しの read が、穴（0 が返るだけで GET が無い）ではなく本当の GET になるようにするため。合計の大きさには上限（既定 32 GiB）を設け、超えたら止めて報告する。中身は圧縮がよく効くので、PUT のバイトは小さく、回数は 4 MiB あたり 1 回になる。[判断]
- 初期状態 [判断]: 種は「ブロックの形・差分なし」の状態で始める。本番の夜を越えた後のような、差分の段が溜まった状態は再現しない。10〜15 分の試験は、差分が溜まり始める時期の動きを見ることになる。まとめ直しと畳み込みは、ほとんど起きない見込み。そのため、溜まった後の動きを見たいときのために、`--age N` を用意する。種を clone した後、計測の前に、記録を既定の設定で N 回流して差分を育てる（既定 0）。
- [source] 起動の hook の基準の数はメモリにある。mount したばかりの試験の volume では覚えていないので、最初は今の x99／350 の条件で動く。本番の mount し直しの直後と同じ。
- 作るのは 1 回で、記録を取り直したときだけ作り直す（触れる chunk が変わるため）。

### 5.4 1 回の試験（`run`）

1. 試験の mount を、その回の compaction の設定で（mount し直して）起動する。
2. 種のファイルを `juicefs clone` で複製する。メタデータだけの複製なので、object は共有され、再アップロードは要らない。
3. キャッシュを温める: キャッシュのディレクトリを空にした状態で、記録の中で読まれる範囲を先に 1 回読む。本番の起動はキャッシュが温まった状態のため。[判断]
4. 計測の suite（`test`）を始める。
5. 記録を流す: 記録の開始の時刻の間隔どおりに、複製のファイルへ同じ操作を発行する。
   - 使う呼び出し: write は `os.pwrite`、read は `os.pread`、fsync は `os.fsync`、fallocate は `fallocate(2)`（ctypes）、大きさの変更は `os.ftruncate`。
   - write の中身は、位置から決まる作り物。
   - 時間は縮めない（Drive が本物のため）。
   - ファイルは普通の `O_RDWR` で開く。O_DIRECT は使わない [判断]。理由は次のとおり。
     - [観測] 本番の QEMU は、raw のファイルを `cache.direct=false, no-flush=true`（cache=unsafe 相当）で使っている。
     - FUSE の writeback_cache は使っていない（2026-10-14 のユーザーの決定）。そのため、ゲストの write は qemu の thread から、ほぼ同じ大きさで FUSE に届く。
   - ゲストの並行は、記録の pid（qemu の thread）ごとに別の thread で再現する [判断]。
   - flush は close のときだけ出るので、流し直しでは最後の close で代える [判断]。
6. 落ち着くまで待つ: staging の待ちが 0、アップロード中が 0、compaction の開始が 60 秒間ない状態。上限は 10 分で、超えたら表に「未収束」と出す。
7. 計測の suite の数字を取り、各操作の待ち時間（中央値、99%、最大）を出す。
8. 複製のファイルを消し、削除の後始末が落ち着くまで待つ。mount を外す。

### 5.5 設定の組と結果（`suite`）

- 既定の組（ユーザーの指示が無ければ、この 6 つ）:
  1. 今の既定（trigger 99、block-ratio 0.5）
  2. trigger 30
  3. trigger 50
  4. trigger 200
  5. block-ratio 0.75
  6. 参考に block モード
- 組は設定ファイル（`settings.toml` など）で書き換えられるようにする。
- 結果は `tests/juicefs/results/<日時>/` に、設定ごとの記録と、全体の比較の表（Markdown）として残す。表の数字ごとに、出どころ（区間と系列）を書く。
- 同じ設定を 2 回流して、ばらつきを見られるようにする（`--repeat`）。

## 6. 安全のための約束

- 本番の Redis の URL には、どの道具も書き込みの命令を送らない。試験の Redis の接続先は、プロファイルで固定し、本番の host と同じなら止まる。
- 試験のバケットの名前が本番のバケット（`buckets`）と同じなら止まる。
- 試験の並列のアップロードは、本番の値以下にする。Drive の回数制限のエラー（429、403 の rate limit）が出たら、その回を止めて表に出す。
- 試験の mountpoint とキャッシュのディレクトリが、本番のものと同じなら止まる。
- 試験が終わったら、clone を消す。試験用のバケットと Redis は残す（次の回で使う）。全部を消す `testvol destroy` は、確認の入力を求める。

## 7. 限界（未検証）

- 種の中身が作り物なので、PUT と GET のバイト数（圧縮後）は本番より小さい。回数と、圧縮前の量で比べる。
- 読み込みの速さ（起動の時間）は参考にしかならない。キャッシュの中身と大きさが本番と違うため。
- 記録は 1 回の起動のものだけ。ゲストの書き込みの形は日によって違う。
- 試験の間、本番と同じ rclone と Drive に負荷がかかる。
