# kaz キャッシュの受け入れ方針（2Q）と compaction の出力の扱い — 設計

作成: 2026-10-19。brainstorming でユーザーと合意した内容をまとめる。根拠の計測は [cache_churn の報告](../../inspection/cache_churn/2026-10-19/report-ja.md)。

## 1. 目的と背景

ユーザーの困りごと:「変更がないはずの部分（OS やアプリの本体）を読むほうが多いのに、なぜ遅いのか」。半日作業した後の VM の再起動や、普段使うアプリの起動で、GET が多発して遅くなる。

計測で分かったこと（2026-10-19、本番 kaz.6、`--cache-size 20G`、`--cache-eviction lru`、`--cache-large-write`、writeback、`--kaz-compaction-mode block`、trash-days 0）:

- 無効なキャッシュ（hidden と partial の見えない部分）は約 5〜7%。dead は 0（retire は機能している）。早期回収は主因ではない。
- 通常の使用中は、キャッシュへの流入が 2 時間で 29.5 GiB（compaction の出力 45%、書き込み 24%、ミスの補充 23%）。20G が約 1.5 周する。アイドル中は約 0.18 GiB/h。
- 使用中に、追い出したブロックを GET で読み直したものが 3.02 GiB（ミスの約 45%）。その多くは追い出してから 30 分以内に読み直した（LRU のスラッシング）。
- 13:10 の VM 再起動（ログインまで 13.5 分、アプリが使えるまで 30.5 分）で GET により補充した 3.45 GiB は、**すべて当日 10:52 の時点ではキャッシュにあり、その後の通常使用中に追い出されたもの**だった。
- OS の起動で読むブロックの多くは、1 回の起動で 1 回だけ読まれ、次に読まれるのは次の起動（推論。追い出し済みリストが要る理由）。

原因は、LRU が「一度しか使われない新しいブロック（書き込み、compaction の出力）」を最新として先頭に入れ、何度も読まれる OS・アプリのブロックを押し出すことである（H2、確認済み）。

## 2. 成功の基準

- **主目標（ユーザーの目安）:** 今日と同じ使い方をしたとき（新しい版を mount し、半日ほど普段どおりに作業してから VM を再起動する）、VM の起動からアプリが使えるまでの GET による補充が、2026-10-19 13:10 の再起動の **1 割以下**（3.45 GiB → 約 0.35 GiB 以下）になること。GET が多発すると遅くなることは分かっているので、GET の量で判定する。
- **判定は、新しい版を入れてから 3 回目の VM 起動で行う（ユーザー決定）。** 2 回目の起動は途中経過として記録する。理由: 1 回目の起動で GET したブロックは新入り用に入り、半日の作業で追い出されて追い出し済みリストに残る。2 回目の起動で再び GET され、そこで常連用に入る。3 回目で初めて、起動のブロックが常連用に揃った状態で測れる。起動と起動の間は、今日と同じく半日ほど普段どおりに作業する。
- 体感（ログインまでの時間、アプリの起動）は参考として記録する。

## 3. ゴール・非ゴール・反ゴール

ゴール:
- 繰り返し読まれるブロック（OS・アプリの本体）を、書き込みと compaction の出力の流入から守る。
- 書いたばかりのデータは、一定の猶予の間はキャッシュに残し、すぐ読み返せばヒットさせる。
- 区別（常連か新入りか）と追い出しの順番を、JuiceFS の再起動（Windows の再起動など）を越えて保つ。
- 効果と調整の根拠になる metrics を出す。

非ゴール:
- 無効なキャッシュの早期回収（効果が小さいと計測で分かった）。
- cache-size の拡大の提案（ユーザー方針: 容量はユーザーが管理する）。
- 起動前の先読み（warmup）や、起動で読むブロックの一覧の記録と再生。
- `--cache-eviction 2-random`／`none`／`lru` の動きの変更。

反ゴール（技術的に動いても失敗とみなすもの）:
- 無改良の JuiceFS が、kaz 版の残したキャッシュのディレクトリを使えなくなる、または誤動作する。
- 容量不足や実保存の失敗を隠す。`--free-space-ratio` による追い出しが効かなくなる。
- staging（アップロード前のブロック）を追い出す、または数え方を変える。
- 書いた直後のデータが、すぐ読み返しても GET になる。
- upstream の更新に載せ直すのが難しくなる（upstream 由来のコードへの大きな変更）。

## 4. 前提と制約（ユーザー方針）

- **無改良の JuiceFS との互換性を失わない。** キャッシュのブロックファイルの名前・配置・中身の形式は変えない。追加の状態は、無改良版が読まない場所（`raw/` の外）に置く。それが無い・壊れている・古いときも安全側で動く。
- **upstream の更新に載せ直しやすい作り**（2026-10-14 からの方針）。判断と状態は kaz 専用のファイルにまとめ、upstream 由来のコードには呼び出しの差し替えや hook 程度しか入れない。既存の例は `compaction_block_kaz.go` と、型アサーションで kaz のインターフェースを探す方法。
- **新しい方式はオプションで選び、既定は今の動きのまま。** 独自オプションの名前は `--kaz-<対象>-<内容>`、ヘルプの先頭に `[kaz]` を付ける。
- fsync、書き込みの順序、read-after-write を弱めない。
- 新規・変更する関数やクラスには、目的が分かるコメントを付ける。

## 5. 決まったこと（ユーザーと合意）

### 5.1 二つの領域（2Q）

- キャッシュを **新入り用（probation）** と **常連用（protected）** に分ける。
- 次のブロックは新入り用に入る。
  - アップロードが終わった書き込み（staging のハードリンク）
  - compaction の出力（5.3 の条件による）
  - read のミスで GET して補充したブロック
- 新入り用にいる間に、**ユーザーの読み込みでもう一度読まれた**ブロックは、常連用に昇格する。
- 新入り用にいる間は、今の LRU と同じくヒットする（書いた直後の読み返しはヒットする）。
- **新入り用の大きさ:** 最初は全体の 3〜5 割程度の決め打ちの既定値とし、オプションで変えられるようにする。正確な既定値はビルダーが決めてよい（計測の流入は使用中 10 分あたり 1〜4 GiB。新入り用 5 GiB なら猶予は約 15〜50 分）。入れた後に metrics で調整する。
- 追い出しは新入り用から先に行う。新入り用の中は、最後に読まれたのが古い順（LRU 相当）でよい。
- **「もう一度読まれた」の判定（agent の判断、ユーザーの確認待ち）:** 1 回の read の中で同じブロックに何度も `load`／`keys.get` が来ることや、readahead も同じ経路を通ることがソースで分かっている。そのため、昇格には古典的な 2Q の「相関期間」を使う。新入り用に入った時刻（または前回の読み込み）から一定時間（既定 10 分程度、オプションで変更可）以上たってからの、ユーザーの読み込みだけを 2 回目と数える。相関期間の中の読み込みは、ヒットとして返すだけで昇格させない（最後に読んだ時刻は更新する）。readahead は区別しない（区別にかかる手間に見合わないと判断）。書いてすぐ読み返したブロックや、GET の直後に同じ流れで読んだブロックは、これで昇格しない。
- **staging は二つの領域のどちらにも数えない（ソースで確認した upstream の数え方に合わせる）:** アップロード前の staging（size<0）は `cache.used` に数えられず、追い出しの対象でもない（`disk_cache.go` の `add`）。新入り用・常連用の容量と取り分は、追い出せるブロック（size>0）だけで計算する。アップロードが終わったときに、新入り用に入る。

### 5.2 追い出し済みリスト（ghost、2Q の A1out）

- 新入り用から追い出したブロックの **名前だけ** を覚える。データは持たない。
- 追い出し済みリストにあるブロックが再び読まれて GET で補充されたら、新入り用ではなく **常連用に直接入れる**。起動で 1 回だけ読まれるブロックや、使用中に 30 分以内に読み直されるブロックを、2 回目で守るため。
- 覚えておく量は、1 日の作業で流れる量を目安にする。キャッシュの容量の数倍、20G なら 60〜100 GiB 分のブロック名で、件数ではなく容量で上限を決める。古いものから忘れる。
- 永続化する（5.4）。

### 5.3 compaction の読み込みと出力

- **compaction の読み込みは、ユーザーの読み込みと区別する。**
  - 昇格させず、最後に読んだ時刻も更新しない。
  - キャッシュに無い元のブロックを GET したときは、そのデータをキャッシュに入れない。
  - 区別の方法（例: `pkg/vfs/compact.go` の読み込みに kaz の印を付ける）はビルダーに任せる。upstream 由来のコードへの変更は最小にする。
- **compaction の出力は、元のブロックの扱いを引き継ぐ。**
  - 元のブロックのどれかが常連用にいれば、出力も常連用に入れる。
  - 元のブロックが新入り用にしか無ければ、出力も新入り用に入れる。
  - 元のブロックがキャッシュに一つも無ければ、出力はキャッシュに入れない。
  - **出力は、元のブロックの「最後に読んだ時刻」も引き継ぐ**（元のうち最も新しいユーザーの読み込みの時刻。compaction した時刻にはしない）。compaction で並び順が崩れないようにするため。
- **`juicefs compact <path>`（ユーザーが時々手で実行する）も対象。** このコマンドは制御ファイル経由で mount 中のプロセスに依頼し、mount の中で `Meta.Compact` を動かす（`cmd/compact.go`、`pkg/vfs/internal.go` の `CompactPath`、ソースで確認）。そのため、背景の compaction と同じ扱い（読み込みは昇格させない、GET した元はキャッシュに入れない、出力は区分と時刻を引き継ぐ）が効く。今の LRU では、このコマンドを VM のディスクに使うと、ファイル全体を読んで最後に読んだ時刻を更新し、キャッシュに無い部分を GET して入れ、出力もすべて入れる。その結果、キャッシュの中身と順番が、使われ方と無関係なファイルの並び順で入れ替わる（ユーザーの指摘）。これを防ぐことも目的に含める。
- **対象は mount 中のプロセスの compaction だけ（agent の判断）。** `juicefs gc --compact` は別のプロセスで、キャッシュは `CacheDir = "memory"`（`cmd/gc.go`、ソースで確認）なので、mount のディスクのキャッシュにも管理ファイルにも触らない。upstream のままとする。
  - `gc --compact` が mount のキャッシュに与える影響（今も新しい方式でも同じ）: mount は元の slice の retire を受け取らないので、元のブロックは dead としてキャッシュに残る（追い出されるまで）。出力の新しい slice は mount のキャッシュに無いので、次に読むときに GET になる。新しい方式では、その GET は新入り用に入り、常連用の dead は降格で抜けるまで場所を取る。
  - **運用での回避（ユーザーへの案内）:** compaction は `juicefs compact <mount のパス>`（ディレクトリは配下のファイルを全部たどる。`baseMeta.Compact` の `walk`）で mount の中で行い、`juicefs gc` は `--compact` なしで使う。これで出力の扱い（区分と時刻の引き継ぎ、元の retire）がすべて効く。
- この扱いは `--cache-large-write` と 4 MiB 未満のブロックを常に入れる upstream の判定（`cached_store.go` の `sync && (blen < BlockSize || CacheLargeWrite)`）より優先する。ただし、新しい方式を選んだときだけ。
- 元のブロックと出力のブロックの対応（ブロック単位の compaction では範囲が対応する）をどの粒度で判定するかは、ビルダーに任せる（出力のブロックごとでも、compaction の 1 回単位でもよい）。

### 5.4 再起動を越えた保存（管理ファイル）

- `raw/` の外（例: キャッシュの UUID ディレクトリの直下）に kaz 用の管理ファイルを置く。無改良版の走査（`scanCached` は `raw/` の下だけ）は読まず、消しもしない。
- 保存するもの:
  - 各ブロックの区分（常連用／新入り用）
  - 最後に読んだ時刻（ユーザーの読み込みの時刻。ディスクの atime は relatime で最大 1 日ずれるため）
  - 追い出し済みリスト
  - 次点として、ブロックごとの由来（書き込み・compaction・GET）とヒット回数（各 1 バイト程度）。metrics と調整のためで、追い出しの判断には使わない。
- 保存は数分ごとと unmount のとき。書き込みは一時ファイルに書いてから rename する（途中で落ちても壊れたファイルを読まない）。
- mount のとき:
  - 管理ファイルと一致するブロックは、区分と時刻を引き継ぐ。
  - 記録の無いブロックは新入り用として扱い、時刻は今と同じく atime から作る。新入り用に入った時刻もこの atime とする（agent の判断）。こうすると、既にキャッシュにあったブロックは、mount の後に初めて読まれた時点で相関期間を過ぎているので、すぐ常連用に上がる（前から入っていた＝以前に読まれたブロックとみなす）。
  - 管理ファイルが無い、壊れている、無改良版で動かした後で古い、といった場合も同じく新入り用として扱う。正しさには影響しない。
- 1 時間ごとの再走査（`scanCached`、`cache-scan-interval`）でも、区分・時刻・追い出し済みリストを失わない。今の atime の引き継ぎ（`lastSnap.peekAtime`）と同じ考え方。

### 5.5 常連用からの追い出し

- 常連用にも上限を設ける（全体から新入り用の取り分を引いた大きさ）。上限を超えたら、常連用の中で最後に読まれたのが一番古いブロックを、**新入り用へ降格させる**（すぐには消さない。降格後にもう一度読まれれば常連用に戻る）。
- **降格したブロックの置き場所（agent の判断）:** 新入り用の中で最も新しい側に置く。最後に読んだ時刻のまま入れると、すぐ次に追い出されて「もう一度チャンスを与える」意味が無くなるため。このため、追い出しの順番を決める時刻（新入り用に入った時刻、降格した時刻）と、永続化する「最後に読んだ時刻」（ユーザーの読み込み）とを、別々に持つ。両方とも管理ファイルに保存する。
- 新入り用には最低限の取り分を保証する。キャッシュが空いているうちは常連用が取り分を超えてもよいが、満杯になったら新入り用が取り分を下回らないように常連用から降格させる。
- 時間による降格（長く読まれない常連を落とす）は入れない。
- ディスクの空き不足（`--free-space-ratio`）による追い出しは、今と同じく区分に関係なく行う。順番は新入り用が先、足りなければ常連用。
- slice の削除（retire）では、区分に関係なくすぐ消す（今と同じ）。追い出し済みリストからも消してよい。

### 5.6 metrics

既存の `juicefs_blockcache_*` は変えずに残し、kaz の metrics を追加する。少なくとも次のものを出す。

- 領域ごとの容量と件数
- 昇格・降格・追い出しの件数
- 追い出し済みリストのヒット（常連用への直接の入り）
- 由来ごとのヒット（書き込み・compaction・GET）。compaction の出力をキャッシュに入れる価値を確かめるため。

名前と形はビルダーに任せる（既存の kaz の metrics に合わせる）。

## 6. 検証

- 単体テストは、外から見える振る舞いで書く。対象は次のとおり。
  - 昇格
  - 追い出しの順番
  - 降格
  - 追い出し済みリストからの直接の昇格
  - compaction の読み込みが昇格させないこと
  - `juicefs compact <path>` の前後で、キャッシュの区分・最後に読んだ時刻の順番・容量の内訳が保たれること（元のブロックは retire で消え、出力が置き換わる）
  - 出力の引き継ぎ
  - 管理ファイルが無い・壊れている・古いときの安全な動き
  - 1 時間ごとの再走査で状態を失わないこと
  - free-space による追い出し
  - staging を追い出さないこと
- 互換性:
  - 新しい方式で動かしたキャッシュのディレクトリを、無改良の JuiceFS（同じ v1.4.1 系）でそのまま mount して、読み書きできること
  - その逆（無改良版の後に新しい方式に戻す）
- 実機（本番。ユーザーが適用する）: 今日の計測の道具（`docs/inspection/cache_churn/2026-10-19/` の `metrics_sampler.sh`、`key_tracker.py`、`timeline.py`、`boot_analysis.py`）で、今日と同じ流れ（半日の作業 → 再起動）を記録する。入れてから 2 回目以降の起動で、2 の基準を判定する。

## 7. ビルダーに任せること

- オプションの名前（`--kaz-` の規則の範囲で）と、新入り用の割合の正確な既定値。
- `KeyIndex`（`pkg/chunk/cache_eviction.go`）の新しい実装として作るか、別の形にするか。ブロックの由来と compaction の読み込みを、kaz のインターフェース（型アサーションで探す）で渡すなどの方法。
- 新しい方式を、`--cache-eviction` の新しい値にするか、別の kaz オプションにするか。ただし既定は今の動きのまま。
- 管理ファイルの形式・名前・保存の間隔（数分ごとの範囲で）。
- 追い出し済みリストのデータ構造。
- compaction の元と出力の対応の粒度。
- metrics の名前と形。

## 8. 追加（2026-10-19 夜）: compaction の出力の扱いの選択と、記録の追加

### 8.1 背景（実機テストの結果）

本番にテスト版（feat/kaz-cache-2q bf9efe73、probation-ratio 0.25）を入れて、3 回目の起動で判定した（[報告](../../inspection/cache_churn/2026-10-19/report-ja.md) の最後の 3 節）。

- アプリが使えるまでの時間は 11.4 分（lru は 30.5 分）。GET で補充した量は 1.03 GiB（lru は 3.45 GiB）で、70% 減った。ただし基準の 0.35 GiB 以下には届かなかった。
- 起動中の常連用 16.69 GiB のうち、compaction の出力が 6.19 GiB（37%）を占めていた。常連用に入ってから一度も読まれていないものは 2.22 GiB。
- 起動で GET したブロックは、18〜19 時台に追い出されていた。最後に読まれたのは前の起動のとき（13・16・17 時台）。
- 推論: 「元のどれかが常連用なら、出力も常連用に入れる」規則（5.3）では、元のブロックが一部しか置き換わらないときに、元も出力も常連用に残る。そのため常連用が膨らみ、次に読まれるのが次の起動になるブロックが、降格・追い出しの対象になった。
- 未確認: 起動で GET したブロックが、降格を経て追い出されたのか。追い出し済みリストに、追い出す前の区分が記録されていないため。

### 8.2 ユーザーの方針

- 検証の起動は次の 1 回だけにする。そのため、記録の追加と修正を同じ版に入れる。
- 実装をやり直す手間を省くため、出力の扱いはアルゴリズムを選べるようにする。候補は「現状」「a」「b」の 3 つ。割合で決める案（c）は見送る。
- 「常連用に入ってから一度も読まれていないものを先に降格させる」案（B）は、次の策として今回は入れない。
- 次の検証では a（`probation`）を使う。

### 8.3 出力の扱いの選択（`--kaz-cache-compaction-placement`）

kaz-2q のときだけ効く。値は次の 3 つ。既定は `inherit`（今の版と同じ動き）。不正な値は Warn して `inherit` にする。

| 値 | 動き |
|---|---|
| `inherit` | 5.3 のまま。元のブロックのどれかが常連用なら常連用、新入り用にしか無ければ新入り用に入れる |
| `probation` | 出力は常に新入り用に入れる。昇格は通常どおり（相関期間の後のユーザーの読み込み、または追い出し済みリスト） |
| `replace` | 常連用にある元のブロックのうち、そのブロックの範囲（ブロックの先頭からブロックの長さまで）が全部この出力に写されたものが一つでもあれば、常連用に入れる。それ以外は新入り用 |

- どの値でも、元のブロックが一つもキャッシュに無いときは、出力をキャッシュに入れない（5.3 と同じ）。
- 最後に読んだ時刻（atime）は、どの値でも、元のブロックの中で最も新しいものを引き継ぐ（5.3 と同じ）。
- `replace` の判定に要る「元のブロックの範囲が全部写されたか」は、出力のブロックごとの元のブロックの対応（`pkg/vfs/compact_cache_kaz.go` の `kazCompactionSources`）で計算する。
- **compaction のモードには関係しない。** upstream のチャンク全体の書き直しでも、ブロック単位の compaction（`--kaz-compaction-mode block`）でも、`juicefs compact` でも、同じ規則が効く。どれも `vfs.Compact` を通るため。

### 8.4 記録の追加

- **追い出し済みリストに、追い出す前の区分を持たせる。** 降格を経て新入り用から追い出したものは「降格を経た」、それ以外は「常連用に上がらなかった」とする。常連用から直接追い出したものは「常連用」とする。
- **ghost_hit を区分ごとに数える。** `kaz_cache_2q_events_total` に、`ghost_hit_demoted`、`ghost_hit_probation`、`ghost_hit_protected` を足す。合計の `ghost_hit` は今のまま残す。
- **区分ごとの容量を由来別にも出す。** `kaz_cache_2q_bytes_by_origin{segment, origin}`（Gauge）を足す。origin は legacy、write、fill、compaction。staging は数えない。
- **管理ファイルの形式を version 2 にする。** 追い出し済みリストの各項目に、区分の 1 バイトを足す。version 1 のファイルも読めるようにし、その区分は不明として扱う（`ghost_hit_probation` に数える）。version 2 を version 1 の版（bf9efe73）で読むと、version 不一致で無視され、全部が新入り用で起動する。無改良の JuiceFS は、このファイルを読まない。
- 調査リポジトリの道具（`progress_kaz.sh`、`state_summary.py`）を、新しい metrics と version 2 に合わせる。

### 8.5 agent の判断

- `probation` に切り替えても、すでに常連用にある compaction の出力は特別に移さない。降格の順に従って入れ替わるのに任せる。半日分の流入（約 30 GiB）で十分に入れ替わる見込み。
- 「降格を経た」の印は、新入り用に降格した時点で項目に付け、昇格したら外す。昇格した後にまた降格したら、もう一度付ける。新入り用にいる間は、印が付いたまま。
- 追い出し済みリストから常連用に直接入った項目（ghost_hit）には、印を付けない（新しく常連用に入ったものとして扱う）。
- 管理ファイルの version 2 では、項目に「印」の 1 バイト（0 か 1）を足し、再起動の後も印を残す。区分のバイト（1／2）の意味は変えない。追い出し済みリストの各項目には「追い出す前の区分」の 1 バイトを足す（0 = 不明、1 = 常連用に上がらなかった、2 = 降格を経た、3 = 常連用、4 = compaction の出力で常連用に上がらなかった）。version 1 のファイルの項目は、印なし・区分不明として読む。
- `ghost_hit` は今のまま 1 回ずつ数え、同時に区分別の 4 つ（demoted／probation／protected／compaction）のどれか 1 つを数える（合計は一致する）。区分が不明（version 1 から読んだもの）は `ghost_hit_probation` に数える。
- `kaz_cache_2q_bytes_by_origin` は、既存の区分の容量と同じく、link／unlink で区分と由来の組ごとに増減し、複数のキャッシュのディレクトリで共有する metrics に差分で出す。由来が途中で変わる場合も、unlink → 変更 → link で数え直す。
- `replace` の判定（agent の判断）: 出力のブロック 1 つごとに、そのブロックに写された元のブロックの範囲を、同じ元のブロックについて piece をまたいで合算する。合算した範囲が、元のブロックの先頭から長さ（元の slice の長さから求める。最後のブロックは短い）までを全部覆えば「全部写された」とする。複数の出力のブロックにまたがって写された元のブロックは、どの出力のブロックでも全部は覆わないので、新入り用になる。ブロック単位の compaction は出力が 1 ブロックなので、この制限はかからない。
- オプションの解釈と検証は、既存の kaz の設定と同じ場所（`pkg/chunk/cache_config_kaz.go`、`cmd/kaz_cache_flags.go`）に置く。不正な値は Warn して `inherit` にし、mount は止めない。`inherit` のときに今の版と動きが変わらないことを、既存のテストが通ることで確かめる。
- 調査リポジトリの道具（`progress_kaz.sh`、`state_summary.py`）の更新は、本体の実装とは別に agent が行う（本体の commit には入れない）。
- （最終レビューを受けた agent の判断）新入り用に入れる compaction の出力は、新入り用の新しい側に入れる（入った時刻と並び順の時刻は「今」）。atime は元の中で最も新しいものを引き継ぐ。並び順まで元の atime にすると、新入り用の一番古い端に入って真っ先に追い出され、「もう一度読まれれば昇格」の機会が無くなるため。常連用に入れる場合の並び順は、今までどおり引き継ぐ。
- 追い出し済みリストの区分に 4 = 「compaction の出力で、常連用に上がらなかった」を足し、`ghost_hit_compaction` で数える（合計は今までどおり一致する）。1 回の検証で「出力の置き場所」と「昇格の条件」を切り分けるため。
- `ghost_hit` と区分別の event は、mount の直後から 0 で出す（差分を取る道具が取りこぼさないように）。

### 8.6 判定

前回と同じ。新しい版を `--kaz-cache-compaction-placement probation` で mount し、半日ほど使う（流入 30 GiB 以上）。その後の再起動で、起動からアプリが使えるまでに GET で補充した量が 0.35 GiB 以下なら成功とする。あわせて、ghost_hit の内訳で、降格を経たものが減っているかを見る。

## 9. 追加（2026-10-20）: 出力の区分を割合で決める（A-c）と、読まれていない常連を先に降格する（B）

### 9.1 背景

- `probation`（§8）での判定（10/20 07:18）: アプリが使えるまで 7.9 分、GET の補充は 0.68 GiB（基準 0.35 は未達）。起動中の ghost_hit は、compaction の出力 110、常連用に上がらなかった 86、降格を経た 9。[報告](../../inspection/cache_churn/2026-10-19/report-ja.md) の最後の節。
- `inherit` では常連用が compaction の出力で膨らみ、降格を経た損失が中心だった（推測）。`probation` では、夜に compaction で作り直された起動のブロックが新入り用に入り、昇格しないまま追い出された。
- 「常連用に上がらなかった」86 の多くは、入れ替え直後の起動で一度だけ読まれたブロックで、次からは追い出し済みリストで常連用に入る見込み（推測）。

### 9.2 ユーザーの決定

- A-c と B を組み合わせて入れる。どちらもオプションで選べるようにする（実装をやり直す手間を省くため）。
- A-c は `--kaz-cache-compaction-placement share`。しきい値は `--kaz-cache-compaction-placement-share-ratio`。
- B は `--kaz-cache-demote-unread-first`（真偽値、既定はオフ）。
- 次の検証は `share`（しきい値 0.5）と B のオンの組み合わせで行う。効かなければ mount し直して切り分ける。

### 9.3 A-c: `share`

- 出力のブロック 1 つごとに、出力のうち穴（Id 0）以外のバイトを分母、**常連用にある元のブロックから写されたバイト**を分子にして割合を出す。割合が `--kaz-cache-compaction-placement-share-ratio`（既定 0.5、0 < x ≤ 1、範囲外は Warn して 0.5）以上なら常連用、未満なら新入り用に入れる。
- 元のブロックが一つもキャッシュに無ければ、出力はキャッシュに入れない（今と同じ）。atime は元の中の最大を引き継ぐ。新入り用に入れるときは新入り用の新しい側に置く（§8.5 と同じ）。
- 写されたバイト数は、出力のブロックごとの元のブロックの対応（`kazCompactionSources`）で、piece をまたいで和集合を取って数える（`replace` の判定と同じ計算）。

### 9.4 B: `--kaz-cache-demote-unread-first`

- 常連用の各項目に「読まれた実績」の印を持たせる。
  - 常連用に入るきっかけがユーザーの読み込み（相関期間の後の昇格、追い出し済みリストからの再取得）なら、印あり。
  - 常連用にいる間にユーザーの読み込みがあれば、印あり。
  - 新入り用に降格したら、印を外す。
  - compaction の出力を常連用に入れるときは、常連用にある元のブロックのどれかに印があれば印あり。
- オンのとき、常連用があふれて降格するときは、**印のない項目を、最後に読まれた時刻の古い順に先に降格**し、印のない項目が無くなってから、印のある項目を同じ順で降格する。オフのときは今と同じ（印に関係なく古い順）。
- 印はオン・オフに関係なく記録する（オフでも metrics で数を見られるようにするため）。

### 9.5 記録と管理ファイル

- metrics: 降格を、印のないもの（`demote_unread`）と印のあるもの（`demote_read`）に分けて数える（合計の `demote` は残す）。常連用の印のない項目の容量を Gauge で出す。
- 管理ファイルを version 3 にして、項目ごとに印を保存する。version 1・2 も読める。そのときの印は、すべて「印なし」とする（実装の後に agent が見直した。ヒット回数で代用すると、移行直後に常連用の 97% が印ありになり、B がほとんど働かないため。印なしで読めば、移行後に読み直されたブロック（起動やアプリのブロック）だけに印が付き、読み直されていない古いブロックが先に降格される）。version 3 のファイルは前の版（57b3de8a）では無視される（全部が新入り用で起動、mount は失敗しない）。

### 9.6 agent の判断

- しきい値の既定は 0.5。
- 割合の分母に穴を含めない（穴は元のデータではないため）。
- version 1・2 から読んだ常連用の項目は、印なしとして扱う（上の 9.5 を参照。当初はヒット回数で代用する予定だった）。
- B がオンのとき、新入り用が空で常連用から直接追い出す場合も、印なしを先にする（降格と同じ順序。heap を 1 本で済ませるため。B の意図とも合う）。

### 9.7 判定と道具

- 判定は §8.6 と同じ（新しい版で mount → 半日・流入 30 GiB 以上 → VM の再起動で、起動中の GET の補充が 0.35 GiB 以下か）。あわせて、ghost_hit の内訳（compaction／降格を経た／上がらなかった）と、`demote_unread`／`demote_read` の比を見る。
- 調査リポジトリの道具（`progress_kaz.sh` に降格の内訳、`state_summary.py` に version 3 と印）の更新は、本体とは別に agent が行う。
- builder check で挙がった細部（割合の分母が 0 なら新入り用、`share` 以外では share-ratio を無視、印の引き継ぎの取り回し、heap の持ち方、v3 の配置、metrics の名前）はビルダーに任せる。

## 10. 追加（2026-10-20 夜）: 何度も作り直される範囲の出力を常連用に入れない（若い出力の判定）

### 10.1 背景

A-c＋B 版の判定（10/20 19:46）: 補充 0.90 GiB（基準 0.35 は未達）。compaction の出力による損失は 16 に減った（A-c は効いた）が、降格を経た損失が 168 に増えた。常連用 15.07 GiB のうち 7.39 GiB を compaction の出力が占め、そのうち 3.72 GiB は入ってから一度も読まれていないのに元の印を引き継いでいた。書き込みが続く範囲（約 2 分ごとに作り直される chunk）の出力が常連用に居座り、起動で読むブロックを押し出した（推論）。[報告](../../inspection/cache_churn/2026-10-19/report-ja.md) の最後の節。

### 10.2 ユーザーの決定

- 「元のブロックの若さで判断する」方法（方法 B）で進める。metadata には手を入れない。
- 検証は軽くする。このリポジトリでの kaz-2q の作業はここで一区切りとし、差分 slice 方式（別セッション）に時間を回す。

### 10.3 動き

- 新しいオプション `--kaz-cache-compaction-hot-age`（既定 0 = 無効。今の動きのまま）。kaz-2q のときだけ効く。不正な値・負の値は Warn して 0。
- compaction の出力の区分を決めるとき、元のブロックのうち「由来が compaction の出力で、キャッシュに入ってから hot-age 未満のもの」を**若い出力**とする。若い出力の元は、
  - 常連用にあっても、`share` の割合の分子（常連用の元から写されたバイト）に数えない。
  - `inherit` と `replace` でも、常連用の元として扱わない。
  - 読まれた実績の印の引き継ぎに使わない。
- 若い出力しか元がない（ほかに常連用の元がない）出力は、新入り用（新しい側）に入る。元が一つもキャッシュに無ければキャッシュしない点、atime の扱いは今と同じ。
- 「キャッシュに入った時刻」は、項目の inserted（compaction の出力として入ったとき、または新入り用に入った時刻）を使う。降格で inserted が変わる点は、ビルダーが扱いを決めてよい（降格された出力は常連用にいないので、判定には影響しにくい）。
- metrics: 若い出力の元を除いたことで新入り用に置いた出力の数を、`kaz_cache_2q_events_total{event="compaction_output_hot"}` で数える（mount 直後から 0 で出す）。

### 10.4 検証（軽く）

- テスト版を `--kaz-cache-compaction-hot-age 30m` を足して mount し、普段どおり 1〜2 時間使う。
- 次を見る（`progress_kaz.sh`、`state_summary.py`）: `compaction_output_hot` が増えること、常連用の compaction の出力の容量が増え続けないこと、常連用の印ありでヒット 0 回の容量が減ること、降格の内訳。
- 判定の再起動（半日の流入の後）は任意とする。
