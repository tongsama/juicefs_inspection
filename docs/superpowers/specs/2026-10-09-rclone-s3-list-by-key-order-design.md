# rclone serve s3：一覧をキーの順に必要な分だけ読む（`--kaz-s3-list-by-key-order`）設計

日付: 2026-10-09
状態: 設計の各節をユーザーが承認済み。この仕様書はレビュー待ち。実装計画は、新しい会話で writing-plans から作る（ユーザーの指示）。

## 1. 背景と目的

`juicefs gc` は、最後に `object.ListAll(chunks/)` で、object storage の全件を一覧する。rclone serve s3（Google Drive）の ListObjectsV2 は、最初のページ（1,000 件）を返す前に、prefix 配下の全ディレクトリ（約 1,400 以上）を Drive から読んで並べ替える。そのため 1 時間以上かかり、JuiceFS の HTTP client の応答ヘッダの待ち（30s 固定、`pkg/object/restful.go:157`）で切られて、gc が FATAL で止まる。詳細は [調査報告](../../../juicefs_gc/2026-10-08/gc-list-timeout-investigation-ja.md)。

今の rclone の一覧（`cmd/serve/s3/list.go` の `entryListR`、`pager.go` の `pager`）には、ほかにも問題がある。

- 2 ページ目以降も、毎回、全件の走査と並べ替えを最初からやり直す。
- マーカー（`start-after`、continuation-token、V1 の `marker`）と完全に一致するキーを探して、その次から返す。一致するキーが無ければ、先頭から返し直す。
- delimiter があるとき、CommonPrefixes を先にまとめて返すので、ページの境目が S3 のキーの順とずれる。
- 要求の context を使っていないので、クライアントが接続を切っても走査が止まらない。

目的: ListObjects（V1、V2）を、キーの順に必要な分だけ読んで 1 ページずつ返す方式にする。1 ページを数秒で返し、`juicefs gc` が最後まで進むようにする。

## 2. 決定事項（ユーザーと合意）

- 直すのは rclone 側（案 (a)）。JuiceFS の gc は変えない（案 (d) は採らない）。
- 新しい方式は、オプション `--kaz-s3-list-by-key-order`（既定は off）で切り替える。本番では on にして使う。
- 「マーカーと完全に一致するキーの次から」の不具合は、オプションに関係なく直す（旧方式でも「マーカーより大きいキーから」にする）。
- 本番で最初に試すときは、`juicefs gc` を `--delete` なしで実行する。

## 3. 新しい一覧の動き（オプションが on のとき）

1. prefix の位置のディレクトリから、深さ優先でたどる。各ディレクトリの中身は、S3 のキーの順に並べ替えてから処理する。比べるときは、ディレクトリを「名前 + `/`」として扱う。これで、`-`、`.`、空白のような `/` より前に来る文字を含む名前でも、S3 の順番（UTF-8 のバイト順）と正確に一致する。
2. マーカー以下のキーは飛ばす。比べ方は「キー > マーカー」で、完全一致は求めない。ディレクトリ `d` の中身のキーはすべて `d/` で始まる。そのため、`d/` で始まるキーがすべてマーカー以下と分かるとき（`d/` がマーカーより小さく、マーカーが `d/` で始まらないとき）は、そのディレクトリを読まずに飛ばす。
3. 返す件数（Contents と CommonPrefixes の合計）が MaxKeys に達したら、続きがもう 1 件あるかだけを確かめる。あれば IsTruncated を true にし、NextMarker を最後に返したキー（または CommonPrefix）にする。MaxKeys が 0 のときは、今の処理と同じく 1,000 として扱う。
4. delimiter が `/` のときは、そのディレクトリだけを読み、子ディレクトリを CommonPrefix として返す。CommonPrefixes と Contents を、キーの順に混ぜて数える。prefix がディレクトリの途中の名前で終わる場合（例 `chunks/0/1`）は、その名前で始まる子だけを対象にする（今の `prefixParser` と同じ分け方）。delimiter が `/` 以外のときは、今の処理と同じ扱いにする（今の処理は `/` 以外の delimiter を区別していない）。
5. ディレクトリを 1 つ読むたびに要求の context を確かめ、取り消されていたら `context.Canceled` で止める。

変わらないこと:

- ディレクトリは、今と同じ VFS の `ReadDirAll`（`getDirEntries`）で読む。ディレクトリのキャッシュ（`--dir-cache-time`）、`--kaz-vfs-lookup-by-path` の扱い、アップロード中の一時 object（`tempObjectPrefix`、`legacyMultipartUploadPrefix`）を隠す条件は、今と同じ。
- 1 ページのために読むのは、根元から今いる場所までのディレクトリ（キャッシュされたもの）と、その先の数ディレクトリだけ。Drive から読むのは、キャッシュに無いディレクトリだけ。全ページを通した Drive の一覧の回数は、今の 1 周分と同じ。

## 4. 作り

- 新しいファイル `cmd/serve/s3/kaz_list.go` に、新しい方式をまとめる。
  - `kazListBucket(ctx, vfs, bucket, prefix, page)`: 入口。prefix をディレクトリの部分と名前の先頭の部分に分け、走査を始める。
  - 走査の本体: ディレクトリを読む → 中身をキーの順に並べる → マーカーと prefix で絞る → object なら加え、ディレクトリなら潜る（delimiter が `/` なら CommonPrefix として加える）。件数が埋まるまで繰り返す。
- `backend.go` の `ListBucket`: bucket の確認と、prefix・delimiter の前処理は共通。オプションが on なら `kazListBucket` を呼び、off なら今の `entryListR` と `pager` を呼ぶ。
- `pager.go`（旧方式）: マーカーの扱いを「完全に一致するキーの次から」から「マーカーより大きいキーから」に変える。それ以外は変えない。
- オプション: `cmd/serve/s3/s3.go` に、ほかの kaz のオプションと同じ形（`Groups: "Kaz"`、ヘルプの先頭に `[kaz]`）で `kaz_s3_list_by_key_order` を追加する。

## 5. エラーの扱い

- ディレクトリを読めない（Drive のエラーなど）ときは、そのままエラーとして返す。今と同じく、JuiceFS 側で再試行される。読めなかったディレクトリを黙って飛ばすことはしない。gc が「一覧に無い＝存在しない」と誤るのを防ぐため。
- prefix のディレクトリが存在しないときは、今と同じく空の一覧を返す。
- 要求が取り消されたら、`context.Canceled` で止める。
- 一覧の途中でディレクトリの中身が変わっても、次のページはマーカーより後ろから読み直すので、重複は起きない。途中で追加された object が入るかどうかは、追加された位置による。これは S3 の一覧の一貫性の範囲内。

## 6. テスト

単体テスト（TDD、`cmd/serve/s3/kaz_list_test.go`）:

1. 全ページの結果の比較（最も重要）: local backend にランダムな木を作る。`-`、`.`、`_` を含む名前、空のディレクトリ、深さの違うディレクトリを混ぜる。MaxKeys を 1、2、3、7、1000 にして、全ページをつなげた結果を、全件を並べ替えた正解と比べる。delimiter あり・なし、prefix あり（ディレクトリの途中の名前で終わるものも含む）で確かめる。
2. マーカー: 存在しないキーを `start-after` に渡したら、その次から返る。continuation-token でも同じ。
3. 途中で打ち切ること: 1 ページ目を返すのに読んだディレクトリの数を数え、全部を読んでいないことを確かめる（VFS の手前、または backend の List で数える）。
4. 取り消し: context を取り消すと、走査が止まってエラーで戻る。
5. エラー: ディレクトリの読み込みに失敗したら、空の一覧ではなくエラーが返る。
6. オプション: off なら、今と同じ結果になる（`pager` のマーカーの修正を除く）。既存の serve s3 のテストがすべて通る（Docker が要る `TestS3Minio` は、これまでどおり除く）。
7. 旧方式の `pager` で、存在しないキーをマーカーにしたとき、その次から返る。

## 7. 本番での確認（ユーザーが実施）

1. rclone を新しいバイナリにして、`--kaz-s3-list-by-key-order` を付けて再起動する。
2. `juicefs gc` を `--delete` なしで実行する。一覧が 30s で切れずに最後まで進むこと、かかった時間、leaked の数が妥当かを見る。
3. rclone のログで、1 ページごとの時間と、Drive の一覧の回数を確かめる。
4. 問題なければ、`--delete` を付けて実行する。

## 8. 範囲外・未確認

- Drive 上に同じ名前の object が重複している場合の扱い（今と同じで、VFS が 1 つにまとめる）。
- gc 全体にかかる時間: Drive のディレクトリ 1 つあたり約 2.7s（前回の観測）とすると、約 1,400 ディレクトリで 1 時間ほど。1 ページずつ返るので、30s の制限には引っかからない。
- ListObjectVersions は対象外（今の rclone は対応していない）。
- JuiceFS の gc 側の変更（ディレクトリごとの一覧への切り替え、案 (d)）は行わない。
