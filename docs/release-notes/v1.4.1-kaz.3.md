# v1.4.1-kaz.3

v1.4.1-kaz.2 に、VM イメージのような巨大ファイルへのランダム I/O で、metadata の待ちを減らす改修を加えた版です。kaz.2 までの改修は、すべてそのまま含みます（[v1.4.1-kaz.2](https://github.com/tongsama/juicefs_inspection/releases/tag/v1.4.1-kaz.2)、[v1.4.1-kaz.1](https://github.com/tongsama/juicefs_inspection/releases/tag/v1.4.1-kaz.1) のリリースノートを参照）。

## 追加したオプション（どちらも既定では無効）

- `--writer-flush-scope=file|range`（既定 `file`）
  - `range` にすると、read と fallocate の前に、ファイル全体ではなく、触る chunk の未 commit の書き込み（と、それが依存する前の slice）だけを commit してから処理します。他の場所への書き込みは止めません。
  - 待ちは file handle のロックの外で行い、ロックを取った後にもう一度確認します。read-after-write の保証は従来と同じです。
  - fsync・close・truncate・copy_file_range は、これまでどおりファイル全体を待ちます。
- `--meta-write-batch=N`（既定 `0` = 無効、最大 1024）
  - 同じ chunk の、続けて commit できる slice を最大 N 個まで、1回の metadata transaction でまとめて commit します。溜まるのを待つことはありません。fsync・close を含むすべての commit に効きます。
  - Redis・SQL・TKV の engine に対応しています。TKV で変更ログ（change log）が有効な場合と、SQL で chunk の slice 数が同期 compaction の閾値（2,500）を超えそうな場合は、1個ずつ commit します。

VM イメージの用途では、`--writer-flush-scope=range --meta-write-batch=64` の組み合わせを想定しています。

## 既定で変わる動作

- **ファイルの mtime が古い時刻に戻らなくなりました。** chunk ごとの commit は並行して進むため、従来は、古い書き込みの commit が後から届くと、mtime がその古い時刻に戻ることがありました（upstream 由来）。commit の順番と mtime の決定を inode ごとにそろえ、この client が記録した最新の時刻より古い mtime を書かないようにしました。`touch -d` などで明示的に指定した時刻は、これまでどおり優先されます。
- 同じ inode の metadata commit は、client の中で1つずつ順に処理されます。従来も metadata 層のロックで順番待ちになっていたため、速度の低下はない想定ですが、計測はしていません。

## 計測結果（qcow2 への Ubuntu Desktop 26.04 インストール）

QEMU は cache=unsafe、qcow2 は新規作成（preallocation=off）、metadata は Redis（RTT 約10ms）、`--debug` 付きです。時間は3回の比較のためのもので、絶対値の目安ではありません。

| | kaz.2 | `range` | `range` ＋ `--meta-write-batch=64` |
|---|---:|---:|---:|
| インストール時間 | 約84分 | 約53分 | 約43分 |
| metadata の transaction 数 | 62,317 | 35,006 | 20,654 |
| fallocate の合計時間 | 3,330s | 1,887s | 1,495s |
| read の合計時間 | 739s | 659s | 332s |

## 注意

- `range` では、範囲外の未 commit の追記が quota や容量のエラーになったとき、そのエラーは fallocate ではなく、後の read・fsync・close で返ります（エラーは記録されて残るので、隠れはしません）。範囲外で後から起きた commit の失敗も、その read では返らず、後の操作で返ります。
- `--meta-write-batch` で、結果が分からないエラー（I/O エラーやネットワークエラー）が batch で起きた場合、その batch の slice は二重登録を避けるために再送せず、ファイルはエラー状態になります。1個の slice が同じエラーになった場合と同じ扱いです。
- SQL（SQLite）と TKV（memkv）は単体テストで確認しました。PostgreSQL・MySQL はソースの確認だけで、実行はしていません。
- 計測は QEMU の cache=unsafe だけです。cache=writeback（ゲストの FLUSH が fdatasync になる条件）での効果は、まだ計測していません。
- SDK や gateway の読み込み（`pkg/fs`）には `--writer-flush-scope` は効きません。
- このほかの注意（Windows 版の mount は未検証、armv7・macOS 向けはなし、稼働中の mount の置き換えなど）は kaz.1 と同じです。
